Memory-constrained inference on a phone

2026 · Galaxy S25 · mobile GPU and flash storage

The question

When a foreground app reduces the memory available to a background LLM, which part of the target model should leave GPU memory: model weights or the K/V cache?

Both can be backed by flash storage, but their costs appear at different points in inference. I implemented both paths on a Galaxy S25 and compared fixed offload configurations with approximately the same reduction in GPU allocation.

Weight versus KV streaming

I implemented separate flash-backed streaming paths for model weights and the K/V cache. The two forms of state have different access patterns: weights are read-only and reused across requests, while the K/V cache is mutable and grows during generation. I/O was overlapped with computation where possible.

Experiments used Qwen3-4B-Q4_0 with a DFlash drafter. The weight- and KV-streaming configurations each reduced GPU allocation by roughly 420 MiB. The selections were fixed throughout each run; this experiment does not yet implement a dynamic eviction policy.

Across two workloads with different prompt and generation balances, neither option consistently dominated. Weight streaming performed better on the workload dominated by prompt processing, while KV streaming was slightly faster on the other workload.

Breaking the requests into prompt processing and generation showed why: the two streaming choices shifted costs between different phases of inference. This suggests that deciding what to evict should depend not only on how much memory must be reclaimed, but also on the expected structure of the request and when the evicted state returns to the critical path.

These measurements are a controlled starting point toward such a policy, rather than evidence for a universal preference for either weights or KV.

Ongoing work

The current comparison uses fixed configurations under controlled conditions. I am extending it toward a calibrated policy that can choose between weight, KV and mixed streaming as available memory and workload behavior change.
