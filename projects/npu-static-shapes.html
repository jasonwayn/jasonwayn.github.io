Speculative decoding on a compiled accelerator

DFlash · Rebellions ATOM+ · four-card server

I ported DFlash to static NPU graphs, profiled the decode loop, and tested four-card scaling. A numerical failure in compiled trigonometry caused acceptance to collapse during long generation.

What I built

Acceptance makes the decode loop dynamic, while this accelerator fixes graph shapes before execution. I used reusable graphs for each stage and kept both KV caches on the device.

01 / PrefillTarget graph, 256-token chunks. Shares its cache with verification.
02 / DraftAppend and block graphs alternate while sharing drafter cache.
03 / VerifyTarget graph checks 16 proposals plus one bonus token in a 17-token shape.

The host commits accepted tokens and schedules the next graph; model work and cache state remain on the device.

Finding the cost of one round

The first one-card port took 96.5 ms per round. I removed redundant cache uploads, bypassed restrictive prefill checks, compiled smaller target shapes with a shared cache, and reduced hidden-state outputs.

Implementation stageRound latency
Initial port96.5 ms
Persistent drafter cache86.5 ms
Unaligned prefill enabled67.3 ms

Hidden-state outputs reduced from 37 to 659.5 ms

Reducing hidden-state outputs from 37 to 6 saved 2.8 ms per round without changing acceptance. Similar savings for small verify and large prefill outputs pointed to per-tensor overhead.

The correctness bug behind falling acceptance

Holding cache length fixed while changing only position reproduced the long-generation acceptance failure. Minimal sin/cos graphs showed maximum error of 1.67 for angles below 4096, enough to corrupt rotary encoding.

I reduced the RoPE angle modulo 2π on the host and kept trigonometry in the compiled graph. This restored drafter output agreement without the slowdown of calculating sine and cosine on the host.

What fixed shapes still require

Three decoder assumptions do not map naturally onto the fixed-shape runtime used here: growing KV caches, different acceptance counts across requests, and control flow that branches on acceptance. An unboundedly growing drafter context does not port directly to this execution model.

fixed shape→fixed context budget→context exceeds budget→select tokens

I tested bounded-context selection, append width, and host scoring. Busy-waiting CPU threads distorted early NPU measurements; passive waiting, avoiding GQA key copies, and reusing scoring storage removed that bottleneck.

On a five-sample, 16K-token pg19 test, selection reached 29.31 tok/s versus 28.62 tok/s for the plain decoder. Repeated scoring added cost without improving acceptance in this DFlash setting; these results do not establish a general long-context speedup.
